# CFHost 1.0 正式版

CFHost 1.0.0 将 CloudflareSpeedTest 测速核心、域名验证、故障修复、Hosts 管理、Tracker 样本验证、下载器反馈与 WebUI 集成为常驻 NAS 服务。本次正式版也加入群晖、飞牛和通用 Linux NAS 的容器部署入口，保留原有威联通部署方式。

**尚未在真实群晖或飞牛设备上运行过 CFHost，也未实测其图形安装界面。** 已完成 Linux amd64 Docker 环境的 Compose、容器启动、WebUI/API、Hosts 写入与备份、数据持久化和重建检查，以及 ARM64 二进制交叉编译。发布工作流构建 amd64 / arm64 镜像，但镜像构建成功不等于在 ARM64 NAS 上运行验证，更不代表所有 NAS 机型或固件版本兼容。

## 版本与安装入口

- 版本：`1.0.0`；源码标签：`cfhost-v1.0.0`。
- 固定多架构镜像：`ghcr.io/zyk1172/qnap-cfst:cfhost-v1.0.0`，用于 Linux amd64 / arm64。
- 固定 amd64 镜像：`ghcr.io/zyk1172/qnap-cfst:cfhost-amd64-v1.0.0`。
- 持续更新标签：`cfhost`、`cfhost-amd64`；旧 QNAP 兼容标签 `qnap-amd64` 继续保留。它们会随主分支更新，不能用于锁定 1.0。
- CFHost 服务层的版本独立于上游 CloudflareSpeedTest 版本；HTTP 网站验证的 User-Agent 为 `CFHost/1.0.0`，`/healthz` 返回服务版本。

## 主要功能

### 1. 测速与候选管理

调用镜像内的 CFST 核心，从 IPv4 / IPv6 地址池测量丢包、延迟和吞吐，按全局门槛筛选候选并缓存结果。支持线程数、测速次数、下载数量 / 时长、下载 URL、任务超时及限流降级设置。

测速结果是当前网络到测速 URL 的观测值，不是目标网站所有请求的真实业务吞吐；网络时段、运营商、Cloudflare 路由、测速源和限流都会影响结果。IPv6 模式需要设备与网络实际具备 IPv6 连通性。完整 CFST 会产生网络流量和一定 CPU / 内存负载，资源较少的 NAS 可降低线程数与下载测试数量。

### 2. 四种域名策略

| 策略 | 选择方式 | 是否独立验证域名 | 结果含义 |
| --- | --- | --- | --- |
| `latency` | loss → delay → speed → IP | 是，按 HTTP / Tracker 模式验证 | 在本次通过验证的候选中优先低丢包、低延迟 |
| `bandwidth` | loss → speed → delay → IP，并满足 bandwidth 门槛 | 是 | 吞吐来自 CFST 测速，不能承诺实际业务带宽 |
| `normal` | delay → loss → speed → IP | 否 | 已选候选，不代表网站或 Tracker 可用；没有新鲜候选时可暂时保留旧映射 |
| `follow` | 复制已有非 follow 目标的最终 IP | 否 | 目标映射已同步，不代表跟随域名自身已验证 |

`follow` 不允许自跟随或 follow → follow 链式依赖，也不会独立测速、HTTP 验证、Tracker announce 或 Transmission 保活。目标停用或无有效映射时，跟随域名转为未解析并移除旧映射。目标重命名可由 WebUI 同步引用；仍被跟随的目标不能直接在 WebUI 删除。旧配置的 `group` 字段不再影响映射选择。

### 3. Smart Repair、单域名维护与 Full Optimize

| 操作 | 范围与行为 | 需要注意 |
| --- | --- | --- |
| Smart Repair | 先验证当前映射，失效后使用新鲜缓存候选；仍失败时按阈值与冷却刷新 CFST | 健康的独立域名通常保留 IP；新的 Transmission 明确连接失败可触发一次即时刷新 |
| 单域名维护 | 只处理所选域名，并同步它的直接跟随域名；必要时立即刷新一次 CFST | 候选池是全局资源，可能刷新；其他独立域名不因此重选映射 |
| Full Optimize | 重新运行 CFST，再处理全部启用域名，允许全局重选 IP | 耗时、流量和映射变化范围更大；周期执行默认关闭 |

维护任务在单实例内按运行状态避免重叠。任务成功或存在映射都不代表所有域名可用，应同时检查未解析列表、探测状态与历史。CFST 超时只限制测速子任务，不是整项维护的绝对时限；域名验证和下载器 RPC 可能使总耗时更长。中断后的任务不会断点续跑，重启后需检查结果并重新执行必要操作。

### 4. HTTP 网站验证

网站验证使用 HTTPS，连接指定候选 IP，并保留目标域名的 Host / TLS SNI。默认严格模式检查 2xx 状态、跳转、正文大小以及 Challenge / 占位页特征，支持失败重试。

默认 HTTP 200 正文最小值为 512 字节；短小的 API 响应、登录页、空内容接口或正常页面中碰巧出现屏蔽关键词，都可能误判。可调整端点、正文门槛、屏蔽规则，或按需要关闭严格模式。关闭严格模式后侧重连通性，部分业务错误状态可能被视为可达。

验证通过只证明本次端点探测符合当前规则，不验证登录、播放、下载、账号权限或完整站点流程。跨域重定向的后续域名使用自身解析，不应把跳转成功理解为同一候选 IP 承载了所有跳转。服务不会自动绕过 Cloudflare Challenge、风控或站点认证。

### 5. Tracker 样本发现与真实 announce

支持手工 `tracker-samples.tsv` 和下载器生成的 `tracker-samples.auto.tsv`，手工样本优先。Transmission 支持新旧 RPC 形式与 Session ID 握手；qBittorrent 通过 WebUI API 读取已完成任务。每个 Tracker 目标域名寻找一个可用的 40 位 v1 info-hash 样本，发现次数与超时可配置。

样本发现本身只读取任务元数据与 Tracker URL，不暂停、恢复、删除任务，也不修改 Tracker 或发 reannounce。读到样本不代表已做真实验证；WebUI 区分未获取、已获取待测试、样本通过、样本失败。

真实样本验证要求 HTTPS announce、候选 IP 上的 TCP/TLS 连接、HTTP 200 和合法完整的 bencode dictionary。当前不支持 UDP Tracker、明文 HTTP Tracker 或纯 v2 info-hash 样本；混合种子只有提供可用 v1 hash 时才能用于此路径。

“样本通过”表示候选可达。未注册种子、账号拒绝、缺参数或其他合法 Tracker 业务错误也可证明可达，不表示 announce 业务成功。明确上游连接失败、非 200、HTML Challenge、空响应、非法 / 截断 bencode 等会判失败。更换 IP 无法修复失效 passkey、账号封禁、种子未注册或站点策略拒绝。

真实验证会使用样本向 Tracker 发请求，并使用生成的 peer ID 与测试参数；不会上传或下载种子内容，也不会替代下载器的正常 announce / 做种统计。是否允许这类请求取决于站点规则，本项目不保证所有 PT 站点接受。发现未取得样本、任务列表被上限截断、权限不足或 API 不兼容时，需要手工样本或进一步排查；“找不到”不等于库中不存在。

### 6. Transmission 健康反馈与保活

Repair 可读取 Transmission 的真实 `tracker_stats`，区分连接失败、timeout、HTTP 403 与已经连接但遭业务拒绝的状态，避免仅凭 CFHost 的主动 probe 判断下载器一定正常。qBittorrent 在 1.0 中提供自动样本发现，没有同等的主动保活与完整运行时健康闭环。

启用 Transmission 连接与真实 Tracker announce，并取得相应样本后，维护可对连接失败的做种任务调用 `torrent-reannounce`。常规保活使用 30 分钟最小重发间隔、每次约 2 分钟观察窗口、最多 3 次尝试；仍失败可进入映射修复。常规容忍门槛要求连接比例至少 90% 且失败数不超过 5，HTTP 403 不受该容忍窗口保护。修复后会重新检查新映射下的状态；观察、业务时间戳与失败分类仍依赖下载器所返回的数据。

这与“自动发现只读”是不同的功能。reannounce 不是重新校验本地文件，不会修复种子数据，但会向站点产生请求。`normal` 与 `follow` 不参与该独立保活路径。样本发现的查询上限不限制完整 Transmission 活跃做种健康扫描，大种子库的 RPC 成本可能更高。

关闭全局自动 Repair 不会取消已经安排的 keepalive 观察，观察到期仍可触发后台 Repair。关闭真实 announce 或禁用 Transmission 连接并保存后，不再执行该保活 RPC 路径，但这不是清空全部后台安排的总暂停按钮；需要完全停止后台操作时应停止容器。维护一次后应检查运行状态。

### 7. Hosts 写入、备份与迁移

只管理自己的 Marker 区块，保留非受管内容。写前备份、原地写入保持 inode、写后重新读取验证；可检测的失败会尝试恢复原内容。支持旧 CF-YX Marker 和旧映射文件迁移。备份默认保留最近 10 份。

默认目标是 NAS 的 `/etc/hosts`，在容器内挂载为 `/host/etc/hosts`。这只作用于使用该系统解析文件的应用，不会自动影响其他 Docker 容器、局域网其他设备、独立 DNS / DoH / 代理解析，也不是 DNS 服务器或整个局域网的网关。

给下载器容器使用共享 Hosts 文件需要单独设置挂载，并保留容器需要的基础记录，详见 [生效范围与配置](https://github.com/zyk1172/Qnap-CFST/blob/cfhost-v1.0.0/deploy/README.md#hosts-生效范围)。更改 RPC URL 不会改变下载器 DNS，解析缓存也可能需要应用重启后更新。

NAS 可能在重启、升级或网络变更时重写系统 Hosts，本版不安装 NAS 系统启动钩子。文件被替换导致 inode 改变时，需要重建容器刷新绑定挂载再应用。原地写入与回滚不能保证断电、外部进程同时修改或介质损坏时完全原子；不要让多个实例同时管理同一个文件，重要配置仍需外部备份。

### 8. GitHub 映射同步

使用 Git Data API 在一次 commit 中发布 `hosts-map.tsv` 与 `status.json`，签名未变化时可跳过重复发布。支持目标仓库、分支、Token 文件和提交说明，默认关闭。

`status.json` 使用 schema 4，包含 `follow_count`；TSV 保留前十列，追加第十一列 `follow_target`。`normal` 行为 `SELECTED`，`follow` 行为 `FOLLOWED`，跟随行不生成独立 HTTP 状态码或验证时间。外部解析脚本应识别表头与 schema，不要假设固定十列。

同步只发布映射和状态，不自动把 Hosts 应用到远端设备，也不备份整个数据目录。网络、Token 权限、目标仓库 / 分支状态可能导致失败；本地 Hosts 成功后同步失败，不会撤销本地写入。默认按映射签名去重，不应把远端状态当作持续实时监控。

### 9. WebUI、历史与持久化

提供 Dashboard、域名编辑、候选 IP、任务进度与历史、实时日志、下载器 / Tracker / 同步设置、样本和运行状态，以及明暗 / Glass / 系统主题、手机布局和快捷命令面板。静态资源随 Go 二进制内嵌，无需额外 Node / Nginx 运行时。

配置、状态、候选和备份保存在 `/data` 对应的持久化目录；最近任务历史最多 200 条，运行日志最多 300 条，不是无限审计日志。`/healthz` 的 `ok` 只表示 Web 服务能响应，不能证明 NAS 挂载可写、CFST 可执行、目标域名成功或下载器在线。

服务面向可信局域网，没有内置登录、多用户权限或 TLS 接入。密码输入框会遮罩显示，但配置 / API / 备份可能包含密码，Tracker 样本文件可能包含 passkey；这些不是加密存储。请按自己的局域网使用条件管理访问与数据，不要将配置和真实样本作为问题附件公开提交。

## 升级、固定版本与恢复

1. 等待当前维护任务结束并停止旧实例，备份整个数据目录、部署 `.env` 和当前目标 Hosts 文件。保留原镜像标签或 digest，备份放在图形项目目录之外。
2. 将 `CFHOST_IMAGE` 设为所需的 1.0 固定标签；保持 `DATA_DIR=/data`、`HOSTS_PATH=/host/etc/hosts` 与原数据挂载，不要新建一个空数据目录代替旧配置。
3. 使用原项目文件运行 `docker compose --env-file .env -f compose.yaml pull` 和 `up -d`；QNAP 专用文件改用 `compose-amd64.yaml`，GUI 按实际文件名重新创建 / 更新项目。仅拉取镜像不会替换运行中的容器。
4. 检查 `/healthz` 的 `version` 为 `1.0.0`，再检查配置开关、样本、下载器 URL、Hosts 挂载、未解析域名与同步结果。先少量手动验证，确认后恢复计划任务。
5. 需要恢复旧版时，使用旧镜像及其对应的数据备份。本项目不保证跨版本降级兼容；镜像回退不代表数据已经回退。

跨 NAS 迁移应先停止旧实例，复制完整数据目录，再调整新设备的数据源路径、Hosts 源路径、下载器地址和访问权限。不要让迁移前后两个实例同时操作同一个 Hosts 文件。
